# 0027. Behaviour changes are kept apart from refactors, and refactors are proven by replay

- **Status:** Accepted (2026-10-09)
- **Source:** the [code review of 2026-10-08](../reviews/code-review-2026-10-08.md) and the owner's answer there; its [bug plan](../plans/review-bugs-2026-10-09.md)

## Context

The review found bugs, performance work and architecture moves in the same modules. Fixing a bug inside a move makes neither checkable: a changed output can't say whether the fix or the move made it. Keeping a known bug so that a move stays byte-identical is no better.

The owner, 2026-10-09: "We'll focus on bugfixes, then architecture, then new features, except in cases where a bugfix would be much easier after an architecture fix (if you recommend them). To explain this order: I'm not fond of mixing bugfixes (behavior modifying) with architecture updates (behavior preserving), nor of trying to preserve known bugs."

## Decision

- **Three kinds of change, never mixed in one step:**
  - bug fixes, which change behaviour
  - refactors and performance work, which don't
  - features
- **Order:** bugs first, then refactors, then features. A bug much easier to fix after a refactor is the exception, recommended to the owner first.
- **A behaviour change found during a refactor isn't made there.** It goes to the owner and joins the next batch of fixes, as C7 and D8 did.
- **A refactor is proven offline, by outputs identical before and after:**
  - the slices' development runs replayed from the committed fixture (`scripts/record_runs.py --replay`), each report as before, no request unrecorded
  - the controlled corpus replayed from its packed fixture (`scripts/controlled.py run --replay`), every report's content as recorded
  - the golden requests unchanged
  - for what those don't cover, the step's own outputs compared: a renderer's pages from the same report documents, the lab's results regenerated byte for byte (`controlled.py score`, `eye_test.py report`), random inputs to a rewritten pure function
  - the full suite
- **A bug fix has a test that fails without it,** raises the reader version where a reader's output changes ([0016](0016-content-reread-when-its-reader-changes.md)), and names the requests it changes, recorded once.

## Consequences

- A replay identical to the one before is the refactor's proof. A changed report is a behaviour change, made in a fix of its own.
- The phase of 2026-10-09 and 2026-10-10 ran this way: 13 architecture items, performance (the replay of the development runs 151 s to about 90 s, the corpus scorer 401 s to 67 s), the clean-ups, and the import cycle through 21 modules broken, each step proven by replay. Two behaviour changes surfaced and became fixes (`--plan` dropped, decision [0026](0026-plan-estimates-dropped.md); the saved comparison's marks).
- Proving a step costs a few minutes of replay and no model calls, because queries are named by their content ([0009](0009-content-addressed-queries.md)) and the fixtures hold their answers ([0006](0006-replay-fixtures.md)).
