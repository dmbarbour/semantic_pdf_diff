# Trials 2026-10-08: the owner's first use on real documents

- **Date:** 2026-10-08. The owner ran the tool on their own documents on another machine. Those documents and runs are private and stay there.
- **Method:** each finding is reproduced or traced here on the public samples, the replay fixtures and the code. The owner's words are quoted; the causes and proposals are Claude's.
- **Status:** findings. Finding 1 is fixed (2026-10-09, the [bug plan](../plans/review-bugs-2026-10-09.md), item 5); finding 5's cause 1 is designed there as item 6. Proposals marked as questions wait for the owner.

## 1. `--fixture` fails when the file doesn't exist yet

**The owner:** "I tried using `--fixture` to create a fixture to record and replay, but it just errored out because the fixture file did not already exist."

- **Reproduced:** `pdf-semantic-diff a b --out DIR --fixture new.sqlite` printed `Error: .../new.sqlite: no such fixture` and exited 1.
- **Cause:**
  - `--fixture-mode` defaults to `replay`, and replay opens a fixture without creating it (`fixtures.open`, `Fixture(create=mode == "record")`).
  - Recording needs `--fixture-mode replay-or-record` (or `record-new`). Neither the help text for `--fixture` nor the error message says so.
- **Also:**
  - The error comes after the sources are scanned into the store, not before.
  - `replay` is the right default for tests and CI, but not for a user who wants answers kept.
- **Proposal:**
  - A fixture named without a mode records and replays, creating the file.
  - Strict replay stays an explicit choice for tests.
  - Options are checked before scanning.
  - This folds into the cache of finding 2.

## 2. Configuration: too many ways in

**The owner:** "I think we need to greatly clean up and simplify configuration. We should keep just a few environment variables, perhaps four: OPENAI_BASE_URL, OPENAI_API_KEY, PDF_DIFF_STORE, PDF_DIFF_CACHE. The difference between STORE and CACHE is that CACHE becomes our answers fixture, perhaps defaulting to $PDF_DIFF_STORE/cache, while STORE is our workspace for a particular difference task. We can also specify store and cache on the CLI. Other configuration items should be adjusted in the store via the CLI, e.g. `pdf-semantic-diff config (set|unset|import|export|show|test)...` with import/export using JSON. Use of `show` should describe options, defaults, examples where feasible."

**Today:**
- **Settings:** 61 of them. Each can be set by an environment variable, `PDF_DIFF_<NAME>`, except the model, which uses `OPENAI_MODEL`. That makes 62 variables, plus `OPENAI_API_KEY` and `OPENAI_BASE_URL`.
- **Other routes in:** a `--config` JSON file, which can also order the levers, and 22 flags on each running command (`add_run_options`).
- **Precedence:** CLI flags, then the file, then the environment, then the defaults.
- **The store binds its settings already:** it keeps every setting that shapes its results. A changed setting asks for `--reset` at run time. The settings are bound, but nothing lets you edit them.
- **The store has two names:** the shortcut command calls its store `--out`, while `compare` calls it `--store`.
- **Two answer caches:**
  - The store's `response_cache` is keyed by query and model, lives inside the store and is cleared with it.
  - The fixture is keyed by query hash and responder, keeps samples and failures, and can be shared and packed.
  - They duplicate each other. The owner's CACHE could be the only one: the fixture format, with `response_cache` retired.
- **Development flags:** `--responder`, `--fixture-mode`, `--fresh-regions` and `--ledger-tag` serve the lab and the tests. They could move to the lab's commands.

**Notes on the proposal (Claude's):**
- **`config set` on a bound setting** can say right away what it will redo, for example "tile and figure regions re-read". That replaces today's `--reset` surprise at run time.
- **`config show`** can be generated from the settings' declarations, which already give the default, class, lever and regions in `docs/configuration.md`. Each setting would add a one-line description and an example.
- **`config test`** can check the endpoint for pennies:
  - it's reachable, and the model is listed
  - a JSON answer parses
  - an image is read, using one card of the eye test, whose random codes can't be guessed
  - it reports the cost
- **`config export` and `config import`** use the JSON settings file's format as it stands (`config.example.json`), the levers' order included.

**Decided, where the cache lives by default:** the owner, 2026-10-08: "The per-user default is tempting. Let's go with that instead."
- A per-user cache (such as `~/.cache/semantic-pdf-diff`) shares answers across tasks unless `PDF_DIFF_CACHE` or the CLI names another, instead of the first proposal's `$PDF_DIFF_STORE/cache`.

## 3. Progress bars are frozen by log lines

**The owner:** "Right now, if there's a mix of progress bars and log outputs, the progress bars previously written are frozen and clutter the screen while a new one is written at the bottom. What we need is something closer to pinned progress bars at the bottom with a rolling log above or similar."

- **Cause:**
  - `progress.Progress` opens one tqdm bar per stage (extract, situate, compare) with `leave=True`.
  - Log lines go to stderr through a plain `logging.StreamHandler` that doesn't know about the bar.
  - So each line, such as "Loaded from store: …", "Scanned …" or a warning, is written over the bar's line. The bar is redrawn below it, and the old copy stays on screen.
- **Proposal:**
  - Pinned bars, with the log scrolling above them: `rich` (`Progress` with `RichHandler` under one live display).
  - It's the library behind Textual, which the tentative *Interactive views* row names, so it moves toward that row instead of away.
  - Without a terminal, today's heartbeat lines stay.
  - A quick stopgap would be tqdm's `logging_redirect_tqdm`, but it doesn't nest bars well (finding 4).

## 4. Totals that keep moving

**The owner:** "the progress bar just kept increasing its max, i.e. 32/40 then 33/48 then later 41/56 (making the numbers up from memory). That's very annoying like a moving goalpost. It would be better to develop some clear concept of what needs processing and base it on that, and use multiple progress bars for hierarchical subtasks that open into more tasks."

- **Cause:** the bar's total counts tasks queued so far, not tasks to do.
  - `run_jobs` feeds pages only while fewer than `2 × workers` requests are pending (8 by default). That keeps image data in memory bounded.
  - So the total runs about 8 ahead of what's done for the whole run.
  - Follow-ups add to it as they arise: continuations, refined halves, table rows, structure queries and reviews.
  - The module says as much: "Totals grow as refinement adds tasks."
- **Proposal:** a hierarchy of bars, each with a total that's fixed once its level opens.
  - **Documents:** known after the scan.
  - **Pages:** a document's page count, known when it opens; worksheets, slides and sections for other formats.
  - **Tasks of a page:** known once the page is segmented.
  - **Follow-ups** open under the task that asked for them, so a page finishes only when everything under it is done.
  - **The ETA** comes from pages, whose total doesn't move. Requests, tokens and cost appear as rates, with no total.
  - `--plan` already counts first-pass tasks without the model, so the same counts could set the totals up front if wanted.

## 5. Image tiles cut through text

**The owner:** "we need to greatly improve our slicing for vision-based claim efforts; I casually browsed the `assets` folder of PNGs from the PDFs, but it was an absolute mess, e.g. quite a few cuts vertically down the center of a paragraph, cutting words left and right, completely useless and producing 0 claims on every query (and even one response where you wrote out, perhaps forwarding from an LLM, "this text is terribly fragmented" or something like that). This may be due to some pages having images around the whole border frame or similar. We probably need a whole plan just to improve tile selection and find/create examples that lead to such perverse outcomes."

**Measured on the public samples** (803 pages: the first 40 pages of every PDF, with default settings):

| Tiling | Pages | Tiles | Text lines cut sideways | Pages with cuts |
|---|---|---|---|---|
| Bands (pages up to 672 pt wide) | 559 | 822 | 0 | 0 |
| Grid (wider pages) | 244 | 6,582 | 6,400 | 236 |

**The recorded answers agree:**
- In the slices fixture, 401 of 964 tile answers (42%) hold no claims.
- 23 answers describe the image as fragments, a "partial fragment" or "a blank or cropped section of a drawing border".
- Of the tiles refined into halves, 28 of 36 answers are empty.

**Four causes, largest first:**

1. **Refinement halves a tile through its text.**
   - A tile whose answer is partial is split at its midpoint along its longer side, with 12 pt of overlap (`Visuals.refine`).
   - The halves aren't grown to whole lines, and their text layer is clipped to the same half-lines. So the model gets fragments in both the image and the text.
   - All 822 bands are wider than tall, so every refined band is cut vertically. On average 5.7 lines cross the cut, and 336 bands have 5 or more.
   - Seen by eye on HabEx's page 4: every line of the paragraph is cut in half.
   - This is the likeliest source of "cuts vertically down the center of a paragraph" on ordinary report pages.
2. **Wide pages fall back to a grid.**
   - Bands are used only on pages up to 1.6 × 420 = 672 pt wide.
   - That excludes slides (720 × 540), landscape Letter (792 × 612), portrait pages slightly larger than Letter (680 to 712 pt wide, the jury sheets) and drawing sheets.
   - Grid tiles are 420 pt with 18% overlap.
   - Growing a tile to whole lines stops at 25% of its size per side, so long lines stay cut.
   - Seen by eye on LCIT's slide 27: a text-only slide, with no drawing and no image, sent as four tiles that each cut every line.
3. **Grid tiles aren't skipped for being text only.**
   - Bands with no graphics are skipped, because text tasks already read them. Grid tiles are dropped only when blank.
   - So text-only slides and landscape pages are read twice, once as text and once as cut tiles.
4. **Decoration counts as graphics** (the owner's frame hypothesis, in part).
   - A band is sent if any drawing or image touches it.
   - Images aren't filtered by size: on 25 pages an image covers over half the page (backgrounds, scans or frames), so every band is sent.
   - Drawings over half the page's height are filtered as frames, but only when they're drawn as one path. Horizontal frame lines and rules still count.
   - In 217 of 822 bands, graphics cover under 5% of the band. Most are likely logos, rules and side bars (HabEx's page 4 has all three), though they haven't been checked one by one.
   - A frame doesn't cut text in bands mode. It sends text-only bands, and with refinement (cause 1) those get cut.

**Proposal:** a plan for tile selection (tentative row in the plans index).
- **Measures without the model:**
  - lines and words cut
  - the share of graphics in a tile
  - tiles that only repeat text tasks
- **Measures with the model:** empty answers, and claims per dollar.
- **A gallery of the worst pages,** found by those measures across the samples.
- **Controlled-document knobs that cause the failures:**
  - a text-only slide
  - a landscape text page
  - a page slightly larger than Letter
  - a border frame, as one path and as four lines
  - a full-page background image
  - logos and side bars
  - a two-column page
- **Candidate fixes, each a lever measured against those cases:**
  - refinement cut at whitespace (gaps between lines, or between columns), with halves grown to whole lines and the text layer taken by whole lines
  - bands on any page whose bands fit the image budget
  - cuts by columns as well as rows (XY-cut)
  - decoration filtered: repeated header and footer graphics across pages, thin rules, frames
  - tiles that are text only skipped on every page
- **Related row:** *Vision profiles and adaptive slicing* (the eye test) sets how small text may get. This plan is about where the cuts go.
